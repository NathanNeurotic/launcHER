# Handoff defect: emulator runs

Analysis report. Copied as written.

## summary

ALL RESULTS BELOW ARE PCSX2 EMULATOR RESULTS (SCPH-39001 BIOS, scratch emulator copy). NOT TESTED on a console. Repository untouched (worktree the handoff worktree still at cfebe01, git status clean; nothing committed). No emulator process of mine is running (0 pcsx2 processes at the end).

Run folders are under <scratch>/pcsx2-tier/runs/ (names cited as evidence). Scripts, scratch sources and scratch ELFs are under <scratch>/handoff-vdyn/ (runs.log there lists every run).

Verdict: the probe's story is real and I could not refute it; I can now state the mechanism with direct evidence, and there are TWO independent handoff defects in the trampoline at cfebe01, plus the symptom is more dangerous than reported.

DEFECT 1 (thread reset writes into POPS text). The four words are written by the BIOS kernel inside the final ExecPS2 syscall, not 40-100 ms later. Call chain (disassembled from RAM, byte-identical to the ROM KERNEL module): ExecPS2 wrapper 0x80002f80 -> __ExecPS2 0x800057e8, loop 0x80005858..0x800058a0 over thread ids 1..255 -> iTerminateThread 0x80003e00 -> thread-reset routine 0x80003bb8, which rebuilds the terminated thread's initial context frame at stack+size-0x2a0 and stores gp/sp/fp/ra at frame+0x1c0/+0x1d0/+0x1e0/+0x1f0, then the thread is deleted. The victim is ps2sdk libkernel's helper thread topThread (thread id 2, priority 0, waiting on its semaphore), whose stack is libkernel's static BSS array stack[0x400]. launcHER's BSS extends past 0x200000 (stack at 0x206040 in the cfebe01 trace build), so stack+0x320/+0x330/+0x340/+0x350 = 0x206360/70/80/90 lie in POPS .text. The four words are the ONLY user-memory words in 0x00100000..0x02000000 that change between 'core copy finished' and 'first instruction at POPS entry'.

The symptom is layout dependent: the words are at &stack+0x320.., and &stack moves with any link change. In two scratch builds whose only change was a larger trampoline, the same four writes landed 0x100/0x200 higher, there was NO trap, Tier 2 'passed', and POPS ran with four corrupted code words. 'No trap' is therefore not a pass criterion; I used 'POPS text 0x200000..0x2497f0 identical to the staged core after POPS has started' instead.

DEFECT 2 (interrupt during the clear/copy). launcHER jumps into the trampoline with interrupts enabled and with ps2sdk's timer system live: INTC 11 (TIM2) -> TimerHandler_callback, DMAC 5 (SIF0) -> _SifCmdIntHandler, T2 free-running with a 113.78 ms period. The trampoline zeroes launcHER (handlers included) and needs ~61 ms (recompiler) / ~74 ms (interpreter) of emulated time before ExecPS2. If T2 overflows in that window the kernel calls the zeroed handler. This is the recompiler crash, and the interpreter has exactly the same exposure: it merely enters with a lucky T2 phase. Forcing the adverse phase under the interpreter kills the handoff 2/2; masking only TIM2, or DI, makes the recompiler run survive the handoff.

FIXES (scratch builds only, nothing in the repo): (a) two-stage ExecPS2, (b) in-place cleanup in C, (c) both - each removes both defects in every run made (no pins, POPS text intact, same POPS log as each other). A layout-preserving, uninstrumented (a) build passes 3/3 where its layout-identical control build traps at 0x00206360 with the same four words.

Remaining differences from the POPSTARTER control are NOT handoff artefacts: an A/B run with launcHER's automatic 'Mode 6 (OSD bypass)' for serial TONYHAX.EXE disabled makes the POPS log match the control (gpu: general read line present, bva=1f000004 at the control's time) apart from device lines. A like-for-like USB run is impossible at cfebe01: launcHER aborts before the handoff on a USB-only setup (ata_bd -200), as the probe reported.

1. **claim:** Lead: the Tier 2 trap at 0x00206360 is the signature of the defect (a run that reaches 'Interlaced (FIELD)' without a trap is a pass).  
   **evidence:** CHANGED. The corrupted addresses are &stack+0x320/+0x330/+0x340/+0x350 and move with the link layout. Scratch builds differing only in trampoline size: 'base' (stack 0x206140) run 20261111T085341-vdyn-base-t2-1 and 'rec' (stack 0x206240) run 20261111T093911-vdyn-rec-interp-1 both reach 'Interlaced (FIELD)' with NO trap, yet four POPS code words are overwritten (rec build: 0x206560 24020025->00203870, 0x206570 24020021->00206620, 0x206580 00c91825->00206620, 0x206590 00f0202b->0012c3e0). ## fix recommendation

Emulator evidence only; any fix still needs a console run.

Both defects must be fixed; each candidate fixes both in the emulator. What differs is robustness and parity.

(a) Two-stage ExecPS2 - smallest and most robust. Tested form (first instructions of the trampoline, before anything is cleared; raw syscall 7 = _ExecPS2, entry = address of the next instruction block, gp 0, argc 0, argv NULL):
    li $sp, 0x0008fff0 ; bal 1f ; nop ; 1: addiu $a0, $ra, (pops_trampoline_stage2 - 1b) ; move $a1,$zero ; move $a2,$zero ; move $a3,$zero ; li $v1, 7 ; syscall ; nop ; pops_trampoline_stage2: lui $s0, 0x0008 ; ori $s0, $s0, 0x4200 ; (existing code from 'li $sp' on, unchanged)
Stage 2 must reload the args pointer itself (registers are not preserved as arguments). The kernel then terminates/deletes topThread while its stack is still launcHER's own BSS, empties the INTC/DMAC handler lists, masks TIM2 and returns with EIE=0, so the clear/copy runs with nothing of launcHER's reachable. It needs no knowledge of which threads, handlers or alarms launcHER (or a future ps2sdk) has, so it also covers device paths I could not test. Cost: one extra '# Restart Without Memory Clear.' (GS/INTC/TIMER/DMAC re-init, about 125 ms before POPS's own) - a visible sequence difference from the POPSTARTER control, which shows a single restart.

(b) In-place cleanup in C before the jump - closest to the control's single restart, but it is a list that must be kept complete: TerminateThread+DeleteThread for every other thread (topThread's id is private to libkernel, so the tested form loops over ids 1..255 and ignores errors), StopTimerSystemTime+EndTimer, SIF command handler removal (SifExitRpc+SifExitCmd or DisableDmac(5)), DI. The thread must be terminated BEFORE the core copy, otherwise the reset frame lands in POPS text again. Tested 3/3 (+1 reduced variant). Anything added to launcHER later (another thread, alarm, handler) silently reopens the defect.

(c) Both - tested 3/3; no measured advantage over (a) in the emulator.

Recommendation: (a), optionally with (b)'s timer stop and DI as defence in depth; choose (b) alone only if matching POPSTARTER's single-restart sequence is ranked above robustness, and take the static verifier's description of the original sequence into account (the control enters at 0x00200000 with one restart; I did not analyse POPSTARTER's code).

Independent of the choice:
1. Replace 'no trap' as the acceptance check by a POPS-text integrity check: after POPS has started, 0x200000..0x2497f0 must equal the staged core (memdiff.py does this from PINE dumps). The current symptom is layout dependent and can be silent.
2. Add an adverse-timer-phase run (delay the trampoline until T2_COUNT is about 0x98xx) to the tier, otherwise the interrupt defect hides behind a lucky phase under the interpreter.
3. The structural cause is that launcHER's data/BSS/heap (0x1fb700 up to and beyond 0x211e60) overlaps the POPS load range; any launcHER thread stack is inside POPS memory. The fixes neutralise this at the handoff; they do not remove the overlap.
4. Separate, pre-handoff items seen on the way (not handoff defects): automatic Mode 6 for .EXE/MENU serials changes POPS behaviour relative to the control for this fixture; USB launch aborts with ata_bd -200 when ps2dev9 is not loaded; thread ids in POPS are shifted by one relative to the control.

## hardware relevance

NOT TESTED on a console; the physical PS2 was not available to me and nothing here is a console result.

What can be said: (1) The writes that corrupt POPS come from the BIOS kernel's own ExecPS2 path (0x80002f80 -> 0x800057e8 -> 0x80003e00 -> 0x80003bb8). PCSX2 does not HLE or patch ExecPS2, thread syscalls or FlushCache (pcsx2/R5900OpcodeImpl.cpp SYSCALL() line 908; case Syscall::ExecPS2 at 982 is debugger-only; fall-through cpuException(0x20) at 1205), and the kernel code in emulated RAM is byte-identical to the KERNEL module of the SCPH-39001 ROM. PCSX2's -fastboot hooks (R5900.cpp eeloadHook/eeloadHook2, called from Interpreter.cpp 639/661) act on EELOAD at the initial ELF launch only. The inputs to that kernel code (TCB of topThread with a stack inside 0x200000..) are produced by launcHER/ps2sdk code that is the same on a console. So for a console with this BIOS revision the same four writes at &stack+0x320.. are the expected outcome - a strong inference, not a measurement. Other BIOS revisions: not examined. (2) The interrupt defect depends only on ps2sdk's timer system being live (T2, 113.78 ms period, handler in launcHER text) while the trampoline zeroes launcHER with interrupts enabled; that configuration is the same on hardware.

What cannot be said: (a) Which symptom a console shows. The corrupted addresses depend on the link layout of the exact ELF installed (trace build: a trap candidate at 0x00206360; other builds: different words, possibly silent). (b) How often the timer race hits on hardware: the clear/copy duration on a real EE was not measured and PCSX2 timing is not cycle accurate; the 61-74 ms window is an emulator figure. (c) Anything about instruction/data cache behaviour: PCSX2 does not emulate the EE caches in these runs (Pcsx2Config.cpp:451 EnableEECache = false), so a missing or misplaced FlushCache cannot show up; the kernel's ExecPS2 path does call its cache-flush routines (0x80002ac0/0x80002a80, from disassembly) and launcHER flushes after copying the trampoline (handler_pops.c 1844-1845), but the two-stage variant's cache correctness on hardware is unverified. (d) Whether POPS then runs correctly on a console with any of the fixes; the emulator only shows POPS text intact and the POPS log matching the control up to device and Mode-6 differences. (e) Recompiler runs say nothing beyond the handoff: POPS does not run under PCSX2's EE recompiler even with the original POPSTARTER.
