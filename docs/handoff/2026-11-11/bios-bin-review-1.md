Written by an independent reviewer of the track. Copied as written.
`<scratch>` paths point at a temporary folder that no longer exists; `<workspace>` is the folder that holds the checkouts. Nothing here was run on a console unless it says so.

## verdict

issues

## issues

1. **severity:** major  
   **description:** The launch-function glue added to launchPOPS in launcher/src/handler_pops.c (the BIOS.BIN probe before the commands, handing the two flags to the config pass, the osd_off carry-over and the -EIO disagreement check, roughly lines 1493-1562) is never executed by any host test; it is only pinned as source text. Two single-line mutants in it survive the feature's tests with both reference inputs set.  
   **evidence:** Mutant E: `if (res >= 0) {` -> `if (res > 0) {` in front of the game-folder probe (so a BIOS.BIN that exists only in the game's folder is never probed: the commands get bios_game=0 and the later real load then trips the -EIO check, i.e. the launch fails). Result on an exported copy of HEAD: test_pops_user_bios.py rc=0 OK, test_pops_launch_hooks.py rc=0 OK (skipped=3), test_pops_fix_files.py rc=0 OK, test_pops_resident.py rc=0 OK. Mutant H: `memset(&romState, 0, sizeof(romState));` removed (uninitialised loader state on the EE stack feeding every gate): same four files all rc=0 OK. Logs: <scratch>/rom-bios-r1-review/mutants_out2.txt  
   **suggested fix:** Move the probe -> commands -> stage -> compare sequence out of launchPOPS into a static helper that the existing host Reader wrapper in tools/test_pops_user_bios.py can build and run on real files (all-games only, game only, both, neither, one too small, probe/load disagreement -> -EIO), and compare the final core with the original's chain for the BIOS-loaded cases.
2. **severity:** major  
   **description:** The new acceptance rule in pops_fix_context_init_builtin (common/src/pops_modes_patches.c, the loop commented 'Accept exactly POPS's own value') is restricted to site 0x2525b0, but no test fails when the restriction is removed, so the 'do not bless arbitrary current bytes' property of that guard is unproven for the code this commit added.  
   **evidence:** Mutant L: dropped `patch->address == 0x002525b0 &&` so the pristine word is accepted at every compatibility site. With both reference inputs: test_pops_user_bios.py rc=0 OK, test_pops_fix_files.py rc=0 OK (31 tests), test_pops_modes.py rc=0 (PASS line printed), test_pops_builtin_db.py rc=0 OK. Practical effect is a weakened consistency check (a core that disagrees with the built-in entry/mask at another site would be accepted instead of rejected); no wrong bytes are written in a consistent launch.  
   **suggested fix:** Add a native test that sets initial_modes (or a built-in entry) for a mode other than 6, leaves that mode's site at POPS's pristine value, and asserts pops_fix_context_init_builtin rejects it, alongside the existing case that 0x2525b0 = 0x1bfc is accepted.
3. **severity:** minor  
   **description:** docs/POPSTARTER_USER_BIOS.md line 42 says of the loader's entry tests 'each word is tested with `bnez`' (the C comment says the same). In FUN_0088019c the entry gates compare the word with 1, not with zero; launcHER tests non-zero.  
   **evidence:** My own Unicorn run of 0x88019c with one gate word set to 2, 0xff, 0x100 or 0xffffffff: 56 isolated cases, 20 differ from launcHER (original loads, launcHER skips). Not reachable in practice as far as I could find: every writer of those words I located stores 0 or 1, and main's own readers use bnez. With values 0/1 only: 298 runs, 104 loads, 0 mismatches.  
   **suggested fix:** Reword to 'compared with 1 in the loader (bnez in main's readers); the words only ever hold 0 or 1' or make the doc silent on the instruction.
4. **severity:** minor  
   **description:** docs/POPSTARTER_USER_BIOS.md section 4 item 1 ends 'The bytes come out the same because the only command writes inside the loaded range are the gated 0x2525b0 ones' without scoping it. It holds when a BIOS.BIN is loaded; without one the older commands-before-files order still changes bytes in a case the doc does not list (item 2 only lists the command text order).  
   **evidence:** My sequence model (original pieces chained in the original's order under emulation vs launcHER's functions in launchPOPS's order, seed 31337, 150 scenarios): with a BIOS.BIN loaded 112 scenarios, 0 differ; with none loaded 38 scenarios, 6 differ, e.g. no BIOS, game-folder PATCH file with mode 6, command $UNDO only: original 0x2525b0 = 0x1bfc, launcHER 0x0648 (flags equal). Output: <scratch>/rom-bios-r1-review/seq_out.txt  
   **suggested fix:** Scope the sentence to 'when a BIOS.BIN is loaded' and add the PATCH-mode-6-then-$UNDO example to the list of older order differences.
5. **severity:** minor  
   **description:** The whole-launch equivalence (probe, commands, both loads, fix files, shell and region) is argued in the doc but not measured by the committed tests as one sequence; each piece is measured separately with preset flags.  
   **evidence:** tools/test_pops_user_bios.py prints seven separate comparisons (loader 224 runs/88 loads, lseek 28, reader 14 + two-folder sequence, shell 131, region 342+18, dispatcher 298, parser 72); none chains the commands with the loads in launchPOPS's order. My own chained model agrees with the original for all 112 BIOS-loaded scenarios, so I found no wrong behaviour here.  
   **suggested fix:** Covered by the helper suggested in the first issue.

## unsupported claims

1. docs/POPSTARTER_USER_BIOS.md line 42 and the matching C comment: 'each word is tested with `bnez`' for the loader's entry tests. In FUN_0088019c the entry gates compare with 1; 20 of 56 runs with other non-zero values differ from launcHER's non-zero test (not reachable with the writers I found).
2. docs/POPSTARTER_USER_BIOS.md section 4 item 1: 'The bytes come out the same ...' is unscoped. Supported by my chained model only when a BIOS.BIN is loaded (112/112); without one, commands-before-files still changes 0x2525b0 in a case the doc does not list (PATCH-file mode 6 then $UNDO: original 0x1bfc, launcHER 0x0648).
3. Commit a3cab9c message and doc: 'the launch first asks pops_user_bios_load() ... and gives the commands those two flags. If the later loads disagree ... the launch stops with -EIO.' This sequence in launchPOPS is asserted by source-text pins only; no test executes it, and two mutants in it (E, H) survive. The described behaviour is plausible from reading the code but is not demonstrated by the tests.
4. Implementer's report that the fix-file position is covered only by a pin / that a position mutant was not run: I ran it (mutant F); it is caught by one source pin and two behavioural Reader tests, so that part is better covered than reported.
5. Anything implying the guard in pops_fix_context_init_builtin accepts 'exactly POPS's own value' only at 0x2525b0 is enforced by tests: the restriction to that site is not tested (mutant L survives).
6. Size test for files of 2 GiB or more: the doc correctly says the original's driver behaviour was not measured; the 32-bit signed compare itself is confirmed only with forced lseek results under emulation, not with real large files.
7. All equality results in the doc and commit messages are emulated/host results; the commit and doc do say 'Not tested on a console' / 'not console runs', which matches what was measured. No claim of a console result was found.
