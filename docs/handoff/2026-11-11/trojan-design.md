# TROJAN_n.BIN: the original's rules and the design

Design report written before implementation. Copied as written.
`<scratch>` paths point at a temporary folder that no longer exists; `<workspace>` is the folder that holds the checkouts. Nothing here was run on a console unless it says so.

## finding reproduced

REPRODUCED, independently (different emulator and different harness than the earlier author). Everything below is host/emulation measurement; NOT TESTED on a console. No repository change was made (worktree the trojan worktree, branch pr23/trojan, HEAD cfebe01, git status clean after the work).

Corpus: REPOP:popstarter/ holds 4,822 fix files: 3,952 TROJAN_n.BIN + 870 PATCH_n.BIN. Unique by sha256 (per kind and slot): 509 TROJAN, 10 PATCH.

Original (POPStarter r13 MAIN unpacked to 0x870000, real POPS core at 0x200000, Unicorn MIPS64, file natives modelled, effects measured by a 32 MiB memory diff after each run, no live write hook):
- TROJAN loader FUN_00880a24: 509/509 unique files print "Hooked", return 1; identical verdict and writes on the mass: and pfs1: call paths; every memory change is explained by one memcpy(load, buf, size) plus one 4-byte hook write equal to `jal entry`.
- PATCH loader FUN_00881de8: 10/10 applied, return 1.

launcHER (common/src compiled to a host DLL, called through ctypes with base 0x200000 / span 0x302e60):
- TROJAN: pops_container_inspect = 0 (OK) for 509/509; pops_container_plan = -3 (POPS_FILE_RANGE) for 509/509; pops_fix_stage = -3 for 509/509. Accepted: 0 of 509.
- WHY: one single rule for all 509 - the payload load range lies outside the core window 0x200000..0x502e60 (the hook IS inside it). The corpus loads at 19 distinct addresses, all between 0x01431000 and 0x0152c3c0. launcher/src/handler_pops.c pops_stage_fix_files then prints "POPS: Fix file rejected %s (%d)" and returns the code, and its caller returns it: the launch is aborted.
- PATCH: 10/10 rc 0, and the resulting staged core is byte-identical to the core the original loader leaves (compared over all 0x302e60 bytes; 0 to 324,236 changed bytes per file).

Header classes of the 509: 507 format 1 / hdr[0xa]=0 / hdr[0xe]=1; 2 format 3 / hdr[0xa]=6 / hdr[0xe]=1 (slot 7, load 0x0146fff0, size 0x304). All load/entry/hook/size 4-aligned; entry inside the payload for all (507 entry == load). Hooks by slot (unique files): 0->0x2327d8 (162), 1->0x2327e0 (40), 2->0x2327e8 (46), 3->0x2327f0 (72), 4->0x232d08 (31), 5->0x232d10 (44), 6->0x232d18 (39), 7->0x2327d0 (21), 8->0x232d20 (33), 9->0x232d28 (21). Payload sizes 48..770,240 bytes (4 files above 0x10000, all slot 0 at 0x01470300).

Additional synthetic probes (36 header variants, original under Unicorn vs launcHER ctypes) show launcHER differs from r13 in both directions: it rejects files r13 applies (hdr[0xe] = 2 or 0xff, unaligned load/hook/size, entry outside payload, hook inside payload, hook 0, any out-of-core load) and it APPLIES files r13 calls Invalid (hdr[0x20] == 0; any of hdr[0x34..0x3f] != 0). r13 with slot 0 invalid and slot 1 valid: returns 1, opens all ten slots, one "Invalid", one "Hooked" (skip-and-continue confirmed by execution).

Scripts (scratch only, never in the repo): <scratch>/trojan-design/ (orig.py, lh.py, corpus.py, diffrun.py, probes.py, probes2.py, patcheq.py, census.py, census2.py, census3.py, census4.py, slotorder2.py; results in records.json, census.json).

## original rules

1. 0x880a40: gp+0x38dc == 1 -> return 0 (all fix-file loaders disabled).
2. 0x880a58: scope (a0) == 1 and gp+0x3460 == 1 -> prints '> SKIPPED !!!', return 0. 0x880a9c: gp+0x3868 != 1 and FUN_008d8958() != 1 and scope != 1 -> gp+0x38dc = 1, return -0x29a.
3. Path, built char by char from 0x880da4: 'pfs1' (gp+0x3448 == 0) or 'mass' (== 1) + ':/POPS' + optional suffix char (gp+0x381c / gp+0x38b8) + '/' [+ title + '/' for scope 1] + 'TROJAN_' + digit + '.BIN'. Slots 0..9 in the loop 0x88106c..0x881d4c (digit bumped at 0x8810cc/0x8810f4). 5. 0x881270: file size < 0x44 -> Invalid (measured: size 0x43 and payload size 0 both Invalid).
6. 0x881280..0x8813b8: hdr[0..7] must equal the 8 characters 'TROJAN_n' of the file being loaded (measured: slot-1 header in a slot-0 file -> Invalid).
7. 0x8813c0: hdr[0xc] == 0 -> Invalid. 0x881430..0x881458: hdr[0xc] must be 1, 2 or 3 (measured: 0 and 4 -> Invalid).
8. 0x8814c4..0x881594: hdr[8], hdr[9], hdr[0xb], hdr[0xd], hdr[0xf], hdr[0x1f] and hdr[0x34..0x3f] must all be 0 (measured Invalid for hdr[8]=1, hdr[0xd]=1, hdr[0x1f]=1, hdr[0x34]=1, hdr[0x38]=1, hdr[0x3f]=1; hdr[0x33]=1 is accepted).

12. 0x881814: hdr[0x20] == 0 (first byte of the name field) -> Invalid.

Measured: rev 5 or 0 with id 7 skipped; rev 6 with id 7 applied; rev 5 with id 0 applied. gp+0x38d8 at this point can only come from the fingerprint matcher FUN_008ff0e4 (called before the fix files); $VCDID_n is parsed later.
15. Every Invalid / Skipped path prints, closes the file, clears the header and continues with the next slot (b 0x881d40). The function returns 1 at 0x881dc8 whatever happened; its call sites 0x876d6c (root TROJAN), 0x877078 (title TROJAN) do not test the return value (only gp+0x38dc is re-read). PATCH call sites: 0x876e00 (root), 0x877118 (title). Order: root TROJAN, root PATCH, title TROJAN, title PATCH.
16. NOT checked by r13 (measured applied): alignment of load/hook/size, load range, hook range (hook 0 writes the word at address 0), entry inside the payload, hook outside the payload.

Hook word: format 2 with hdr[0xa] == 1 -> `j entry` (4 bytes, 0x881b14); == 2 -> `j entry` + 4 zero bytes at hook+4; == 3 -> `j entry` + 8 zero bytes at hook+4; everything else (format 1, format 3, format 2 with width 0 or >= 4) -> `jal entry` 4 bytes at 0x881c38, word 0x0c000000 | ((entry >> 2) & 0x3ffffff). 19. Precedence at 0x232d08 (last writer wins; from the address order of the writers in MAIN and the repo's docs, NOT from an end-to-end emulated launch): fingerprint built-in entry writes `jal 0x01460000` (FUN_008d6da4, matcher calls at 0x8757d4..0x8769ac, before the fix files) < root TROJAN_4 < title TROJAN_4 < config parse $BREAKPOINT0/1 (0x8962e8/0x896534) and $VCDID_n breakpoint entries < $RESET_WARMBOOT (0x8795f0 builds lui/ori/sw into 0x232d00..0x232d08, so the slot word becomes the store and nothing is called from it). ## payload dependencies

Static census of the 509 unique TROJAN payloads (own decoder, checked against capstone listings): recursive descent from the header entry plus every in-payload address that a formed `j`/`jal` word targets; per straight-line constant tracking (lui + ori/addiu; lui base + offset loads/stores; gp-relative as POPS gp 0x50a670). 39,613 code words reached; 630,585 nonzero words not reached (almost all in the 4 large slot-0 payloads: data). Zero indirect jr/jalr with a non-constant register. Static only: computed or data-driven references are not seen, so every "needs only" count is a lower bound on dependencies.

Entry path (the code that runs inside the GP1 chain), all 509: writes only k0, k1 and (467) ra; reads no register before writing it except ra (42); never touches sp. Return: 467 return with a HARD-CODED `lui ra / ori ra / jr ra` to hook+8 (0x2327d8 x20, 0x2327e0 x129, 0x2327e8 x39, 0x2327f0 x45, 0x2327f8 x71, 0x232d10 x30, 0x232d18 x43, 0x232d20 x38, 0x232d28 x32, 0x232d30 x20); 42 return with the jal's ra. 132 payloads store to their own hook word (130 store 0, a one-shot; 2 re-point it into the payload).

(a) POPS core. Text: stores to 36 distinct addresses (195 payloads; e.g. 0x22e424 x110, 0x23b0ec x110, 0x22e420 x100, 0x23ad0c x100, 0x23acb0 x100, 0x20cce8 x24), loads from 55 (283 payloads; payloads compare the existing word before patching), direct jumps back to 28 addresses (97 payloads; e.g. 0x208b10 x18, 0x20b100 x13, 0x211980 x13), calls to 0x2114b0 (x13) and 0x208568 (x6). Data: stores 29 addresses (106 payloads; 0x502680 x100), loads 0x4f83c0 (x100). BSS: stores 10 addresses (28 payloads), loads 26 (66 payloads). 118 payloads use gp-relative data, 100 contain syscall 2 (190 occurrences, in installed routines, not on the entry path).
(b) POPStarter's copied blocks. Block 1 (0x232790..0x232ec8): only the slot words and their hook+8 landings, as above; no other block-1 address. Block 2 (0x238a90..0x2397f0): 137 payloads - 120 reference POPStarter's 480p handler internals at 0x2394f0..0x239757 (stores to 0x2394f0/4 x100, 0x239500 x120, 0x239548/c x120, 0x2395a4 x20, 0x2395dc x110, 0x239634 x110, 0x2396cc/d4 x30, 0x23970c x30, 0x239748 x100, 0x239750 x20; jumps into 0x2395ac and 0x23969c x20; `j 0x2394f0` installed x30); 17 reference the tail slot 0x2397d8 (load x14, store x9).

## memory map conflicts

Corpus load ranges (19 distinct load addresses): 0x01431000..0x01431230, 0x01432000..0x014322f0, 0x01433000..0x01433070 (150 unique files), 0x0146cf80..0x014702f4 (212), 0x01470300..0x0152c3c0 (147; four payloads of 0x9f0c0..0xbc0c0 bytes). One family also writes 0x01430000..0x01430067 at run time.

launcHER at RUN time (after handoff): resident 0x0143a000..0x01460000 (POPS_RESIDENT_BASE/LIMIT), built-in fix code 0x01410000..0x01420000, breakpoint handler 0x01460000..0x01460200. Measured overlap of corpus LOAD ranges with each of these: 0 files. PS1 RAM 0x01000000..0x01200000: 0 files. But 5 payloads REFERENCE 0x0143a048 / 0x0143a6b8 expecting POPStarter's contents there, where launcHER has its resident: a real address conflict (those payloads would jump into or read unrelated resident bytes).

launcHER at STAGING time (while fix files are read, handler_pops.c line ~1450): every corpus range lies inside the staging area. The staged core is 0x01000000..0x01302e60; the loose-ELF staging span runs to 0x01665940 (staged BSS, not used after pops_boot_stage_elf); with a PAK the decoded image, including the IOP image used for the later IOP reboot, sits in the same 8 MiB buffer 0x01000000..0x01800000. IOP buffers 0x01700000 / 0x01780000, raw input 0x01800000, fix-file scratch 0x01f00000 (1 MiB), scratch folder staging 0x01f80000. So a payload cannot be memcpy'd to its EE address when the file is read (r13 does exactly that): it has to be held and copied at the point where launcHER already installs the built-in EE code and the resident (handler_pops.c lines ~1811..1840, after the IOP reboot, before the trampoline). The trampoline (launcher/src/pops_trampoline.S) only zeroes the scratch folder, 0x502e60..0x870000 and 0x100000..0x200000 and copies the core to 0x200000, so memory at 0x0142xxxx..0x0152xxxx written before it survives into POPS.

Inside the POPS core: launcHER's staged core still holds POPS's own code at the ten hook addresses and their hook+8 landings (0x2327d0..0x2327ff is inside a POPS function starting at 0x232790; 0x232d08..0x232d37 inside another). r13 overwrites all of 0x232790..0x232ec8 (0x738 bytes) and 0x238a90..0x2397f0 (0xd60 bytes) on every launch. Measured on the pinned core: 0 j/jal targets, 0 data-word pointers and 0 lui/addiu-formed addresses into 0x232790..0x232ec8; 10 jal references from POPS text into 0x238a90..0x2397f0 (e.g. 0x23850c -> 0x238fd0). Writing a `jal entry` at a slot address today would corrupt a POPS function without making the payload work, and 467 payloads return to an absolute hook+8 that today is POPS code.

POPS's own use of high memory: crt0 SetupHeap(0x865940, -1) and a 0x100000 stack at the top of RAM; whether POPS's heap can reach 0x0142xxxx was NOT measured. r13, its built-in code at 0x01410000 / 0x01460000 and the whole corpus rely on it not doing so, and launcHER already places code there.

## slot semantics

Measured by running POPStarter's two resident blocks as relocated (MAIN 0x983150 -> 0x232790, 0x738 bytes; 0x983890 -> 0x238a90, 0xd60 bytes; `j 0x238a90` at 0x232d30 as the launch writes it) over the real POPS core on the repo's own interpreter tools/r5900_mini.py (imported read-only), from the entry 0x239490 to the return, with a recording stub hooked as `jal stub` on all ten addresses, once returning with the jal's ra and once with ra := hook+8. Emulation only; NOT TESTED on a console.

Entry: POPS's GP1 write path reaches 0x21a63c, where r13 puts `jal 0x239490`; the word at 0x21a640 is `di` (0x42000039), executed in the delay slot. 0x239490 saves k0 and k1 with sq into 0x2394d0 / 0x2394e0, then branches to 0x232790. Exit 0x2394b0 restores them with lq, REBUILDS ra as the constant 0x21a640 and jumps there (so `di` runs a second time; launcHER returns to 0x21a644).

Order per GP1 write (identical for both return conventions):
entry 0x239490 -> emode combos 0x232790..0x2327cc -> slot 7 (0x2327d0) -> slot 0 (0x2327d8) -> slot 1 (0x2327e0) -> slot 2 (0x2327e8) -> slot 3 (0x2327f0) -> 0x2327f8 lid / $SCANLINES / in-game disc swap / slot copies / $NOVMC0/1 stores -> controller-ID stores 0x232cb0 -> reset combo 0x232ce8..0x232d04 -> slot 4 (0x232d08) -> slot 5 (0x232d10) -> slot 6 (0x232d18) -> slot 8 (0x232d20) -> slot 9 (0x232d28) -> 0x232d30 `j 0x238a90` -> $SET_TIMINGS block -> 0x238d00 (second LibCrypt slot) -> tail slots, 0x2397d8 (game-fix call slot) -> 0x2397e8 (`b 0x2394b0`, where cheat code goes) -> exit.
Each empty slot is the pair 0x10000001, 0x00000000 (`b +8; nop`).

Against launcHER's pops_resident_gp1_work (common/src/pops_resident_engine.c:686): slots 7,0,1,2,3 fall INSIDE pops_resident_hotkeys, between its emode checks and its lid-open check; slots 4,5,6,8,9 fall right after the reset-combo store, i.e. exactly where the POPS_RES_F_BREAK_CALL call is today (0x232d08 IS that slot), and before pops_resident_timings, the LibCrypt2 code, the POPS_RES_F_FIX_CALL call (0x2397d8) and the cheats.

State a payload is called with (measured at every stub): ra = hook+8; sp, gp (0x50a670), at, v0, a0, t0, s0 exactly as POPS had them at 0x21a63c (the block code itself uses only k0/k1); k0/k1 hold whatever the chain or the previous payload left (at slot 7: k0 = 0, k1 = the emode compare value; not preserved between slots); interrupts disabled; POPS thread stack, sp untouched by the chain. At the return into POPS: k0/k1 restored to their entry values, ra = 0x21a640, every other register unchanged. So a payload may clobber k0, k1 and ra freely; anything else it changes reaches POPS (launcHER's own comment: POPS still needs v1 afterwards). All 509 corpus entry paths stay within k0/k1/ra.

Return conventions that must both work: `jr ra` with the jal's ra (42 corpus files) and an absolute jump to hook+8 (467 files). The second one needs real code at 0x2327d8/e0/e8/f0/f8 and 0x232d10/18/20/28/30, the next slot or the continuation.

Precedence at 0x232d08: see the last-writer order in original_rules (built-in `jal 0x01460000` < root TROJAN_4 < title TROJAN_4 < $BREAKPOINTn / $VCDID_n < $RESET_WARMBOOT store). Measured piece: a format-1 TROJAN_4 writes `jal entry` at 0x232d08. launcHER today applies config patches BEFORE fix files and already clears the break call under $RESET_WARMBOOT (handler_pops.c:1517, quirk 25), so the TROJAN_4 / $BREAKPOINTn case has to be resolved explicitly, not by write order. Format 2 with width 2 or 3 writes zeros at hook+4 (the slot's own nop) and, for width 3, at hook+8, which is the NEXT slot's hook word; files are processed in slot order 0..9 while the chain runs 7,0,1,2,3 / 4,5,6,8,9, so a width-3 TROJAN_7 erases a TROJAN_0 hook written earlier (r13 behaviour, to be reproduced by doing the same writes in the same order).

## design

SCOPE, stated first: FULL support of the corpus is NOT achievable now. What is achievable now is (Stage 1) r13's exact verdicts with skip-and-continue instead of the launch abort, and (Stage 2) hosting the payloads that need nothing of POPStarter's beyond the slot chain: 367 of 509 unique files (3,744 of 3,952 corpus copies) by static analysis. The other 142 unique files (208 copies) stay unsupported and must be reported as such. Nothing here is console-tested; no stage may be presented as compatibility until it is. Stage 1 alone makes the launch survive but loads NONE of the 509 files: the docs row stays PARTIAL.

STAGE 1 - exact verdicts, skip-and-continue (minimal correct step)
1. common/include/pops_external.h, common/src/pops_external.c: new pure function pops_trojan_verdict(file, size, slot, fingerprint_builtin_id, PopsTrojanInfo *out) returning APPLY / INVALID / OUTDATED in r13's rule order (rules listed in original_rules: size < 0x44; name == 'TROJAN_n' of the slot; format 1..3; hdr[8],[9],[0xb],[0xd],[0xf],[0x1f],[0x34..0x3f] zero; load != 0; entry != 0; 0x40 + 24-bit size == file size; hdr[0xe] != 0 (any nonzero); hdr[0x20] != 0; format 1 needs hdr[0xa] == 0; format 3 with hdr[0xa] < 6 and a fingerprint-matched built-in id -> OUTDATED). out carries format, width, load, entry, hook, size and the 1..3 hook words (jal, or j plus zero words). POPS_TROJAN_REVISION = 6 as a documented constant (0x870d9c). This fixes both measured directions (launcHER currently applies hdr[0x20] == 0 and hdr[0x34..0x3f] != 0 files and refuses hdr[0xe] >= 2).
2. common/src/pops_modes_patches.c pops_fix_stage (TROJAN branch): verdict first. Return 0 applied; positive POPS_FIX_SKIP_INVALID / POPS_FIX_SKIP_OUTDATED / POPS_FIX_SKIP_UNHOSTED (with a reason enum: outside arena, overlaps launcHER memory, unaligned, hook not hostable, references POPStarter 480p handler / tail slot / built-in code / resident region, no hold space); negative only for internal errors (a guard mismatch in the staged core stays fatal). The built-in id passed in must be the fingerprint one only.
3. launcher/src/handler_pops.c pops_stage_fix_files: positive results print r13's own words ("Invalid", "Skipped (outdated)") or, for UNHOSTED, an explicit line that the file is valid for POPStarter, is NOT loaded by launcHER, and why; then continue with the next slot. Negative results and read errors other than ENOENT stay fatal (r13 treats every open failure as NOT FOUND; keeping launcHER stricter is a logged deviation). PATCH keeps its present behaviour until FUN_00881de8's Invalid rules are re-derived the same way (first task of this stage); the 10 corpus PATCH files already give a byte-identical core.
4. Tests. tools/test_pops_external.py and tools/test_pops_fix_files.py, three classes as elsewhere: Native (CI, no inputs) - the 36 + 11 synthetic header cases measured here as a table of expected verdicts and hook words; Original (skipped unless POPSTARTER_TEST_ELF and POPS_TEST_ELF) - the same synthetic files through FUN_00880a24 under emulation, asserting verdict, hook word(s), memcpy destination and that slot n+1 is still processed after an invalid slot n; Source - the handler fragment: invalid slot 0 + valid slot 1 does not abort, messages, I/O error still aborts.

STAGE 2 - the slot chain and out-of-core payloads (implementable and host-testable now; NOT console-tested)
A. Slot skeleton in the staged core (common/src/pops_resident.c, new pops_slot_chain_install(staged_core, core_size, resume_a, resume_b)): after verifying the pristine POPS bytes of 0x2327d0..0x2327ff and 0x232d08..0x232d37 (a checksum of the two 0x30-byte ranges, or the 24 words as documented constants), write five `b +8; nop` pairs at 0x2327d0..0x2327f7 and `j resume_a; nop` at 0x2327f8; five pairs at 0x232d08..0x232d2f and `j resume_b; nop` at 0x232d30. Same addresses and same empty-slot words as r13, so both return conventions and the payloads' stores to their own hook work unchanged. Installed lazily, only when the first slot-hooked TROJAN is accepted, so launches without TROJAN files keep today's core bytes. Justification for overwriting: r13 overwrites the whole 0x232790..0x232ec8 on every launch and the pinned core has no static reference into it.

## blockers

1. Full corpus support is NOT achievable now. feasible_now = true covers only Stage 1 (exact verdicts, skip-and-continue) and Stage 2 (367 of 509 unique files, 3,744 of 3,952 copies, by static analysis). 142 unique files (208 copies) remain unsupported.
2. Nothing is console-tested. Stage 2 changes the GP1 path that runs on every GP1 write and overwrites 0x60 bytes of POPS code; it needs console validation with real fix files before any compatibility claim. Until then the docs row must stay PARTIAL.
3. Stage 1 alone loads none of the 509 corpus files: the launch no longer aborts, but every corpus TROJAN is skipped with a message. That is a correct minimal step, not support.
4. Owner decision needed: a file r13 applies but launcHER cannot host - skip with a visible warning and continue (recommended, used in the design) or keep aborting the launch. Skipping is a deviation from r13 either way and must be logged as a quirk.
5. 480p-handler family (120 unique, 158 copies): these payloads rewrite and jump into POPStarter's own 480p handler at 0x2394f0..0x239757 (14 store sites, 2 jump-in targets). Supporting them needs code with POPStarter's instruction layout at those addresses, i.e. reproducing about 0x268 bytes of POPStarter code, which the no-copy rule forbids; launcHER's handler is C in the resident at another address. No compliant approach identified.
6. Tail-slot / built-in family (17 unique, 36 copies): they read or write the 0x2397d8 game-fix slot and 14 install `jal 0x01410000`. What r13 has at 0x01410000 when no built-in entry matched, and how a third chain segment at 0x2397d8 would interact with POPS_RES_F_FIX_CALL, was not analysed.
7. Resident-address family (5 unique, 14 copies): they use POPStarter's contents at 0x0143a048 / 0x0143a6b8, where launcHER's resident lives. Unsupportable without moving the resident or emulating those entry points.
8. The static scan cannot prove a payload independent of POPStarter: computed or data-driven references are invisible to it. A payload it accepts may still misbehave at run time; the 367 figure is an upper bound on what works, not a measurement of what works.
9. Not measured: whether POPS's heap or any POPS allocation can reach 0x01420000..0x01600000 at run time (r13 and the corpus assume not); whether POPS ever executes its own code at 0x2327d0..0x2327ff / 0x232d08..0x232d37 (statically unreferenced, and r13 always overwrites it).
10. Not analysed: interaction between launcHER's own core patches and the POPS words that hostable payloads compare or patch (8 such words are named in launcHER's sources).
11. The precedence at 0x232d08 comes from the order of the writers in MAIN and the repo's docs, not from an end-to-end emulated launch with a TROJAN_4 plus $BREAKPOINTn / $RESET_WARMBOOT.
12. PATCH loader FUN_00881de8: Invalid rules not re-derived line by line; only the 10 corpus files were compared (byte-identical core). PATCH skip-and-continue should wait for that.
13. Implementation checks still open: that 0x01800000..0x01f00000 is unused between staging and handoff (hold arena), and the PAK case where the IOP image shares the staging buffer.
