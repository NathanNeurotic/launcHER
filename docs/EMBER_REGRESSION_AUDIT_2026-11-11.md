# EMBER regression audit of the POPStarter-replacement branch (2026-11-11)

Question: for a user who never launches a PS1 game, does anything that worked
on `EMBER` behave differently on `codex/popstarter-replacement`?

Answer at `cfebe01`: **yes**. Earlier commits on this branch changed shared
launch code. The verified findings are listed below; the three rated high are

1. USB / MX4SIO / i.Link driver init tries a live-IOP load with added sleeps
   and forced tolerance before (or instead of) EMBER's IOP reset
   (`launcher/src/init.c`).
2. `ata_bd` is in the USB module set while `ps2dev9` is not, so the
   non-tolerant reset path for a USB launch stops at `ata_bd`.
3. An explicit `rom0:`/`rom1:`/`rom2:` target is tried as `<target>.VCD`
   first, and `LoadExecPS2` does not return to try the real path
   (`launcher/src/main.c`, `common/src/launch_args.c`).

How this was produced, and its limits:

- Read-only: four auditors read `git diff origin/EMBER HEAD` by area; each
  claimed change was then given to a second agent told to refute it by reading
  both sides. Nothing was built or run. **NOT TESTED** on a console or in an
  emulator; console outcomes below are inferences from the code unless stated.
- The IOP-module area (`launcher/iop`, `launcher/irx`) was **not audited** in
  this pass, and the last two `ee-handlers` items have no second-agent verdict
  (marked UNVERIFIED).
- `REAL / <severity>` is the second agent's verdict. The "verifier" line is
  its corrected statement and supersedes the auditor's old/new text where the
  two differ.
- Status: a fix track (restore EMBER's behaviour for non-PS1 launches, keep
  the PS1 path) was started the same day; this file records the state before
  it.

### [REAL / high] USB / MX4SIO / i.Link driver init no longer resets the IOP first: new live-IOP 'fast path' with added 3 s + 3 s sleeps and forced tolerance
- where: launcher/src/init.c:251-276 (loadModules), 338-359 (loadModuleListResident); reached from handleBDM -> initModules(device) (launcher/src/handler_bdm.c:31) and handleQuickboot for every non-POPS BDM launch
- old: EMBER loadModules always did sceSifInitRpc -> SifIopReset -> sbv patches -> load exactly the module set for the device, failing hard on any module error (tolerant=0). No sleeps. The target ELF inherited a freshly reset IOP holding only launcHER's drivers.
- new: For any request containing Device_USB, Device_MX4SIO or Device_iLink, loadModules first (a) sleeps 3 s if USB (init.c:268-269), (b) calls loadModuleListResident, which loads the whole module list onto the LIVE, un-reset IOP with tolerant hard-coded to 1 (init.c:351; the caller's tolerant argument is ignored) and deferFileXioInit=1, (c) sleeps another 3 s (init.c:357), (d) binds fileXio. If that returns 0 the IOP is never reset (init.c:271-273). Consequences shown by the code: at least +6 s on every USB launch and +3 s on MX4SIO/i.Link; non-Basic driver load failures (usbd_mini, usbmass_bd_mini, mx4sio_bd_mini, iLinkman, bdm...) are silently swallowed and reported as success, so the reset fallback is NOT taken for them; sbv_patch_fileio / sbv_patch_disable_prefix_check / sceSifInitRpc(0) are not run on this path; the target ELF inherits whatever foreign modules the previous program left resident plus launcHER's. The 'skip already-resident modules' loop at init.c:343-350 is a no-op (both branches only continue; loadModuleList at 351 then loads every module regardless), so the comment 'Duplicate-load-safe: already-resident libraries are skipped' (init.c:261) is not what the code does. A Basic-module failure on the live IOP prints 'ERROR: Failed to initialize module ...' via msg() (init.c:459-461, initialises the debug screen) before falling back to the reset path. The commit that added this (d42763f) cites only ps2link-rig evidence.
- affects non-POPS users: Yes - every non-POPS ELF launch from mass:/usb:, mx4sio: or ilink: (including the README's Ember flows). Slower at minimum; functional outcome on a standalone console depends on what is resident on the live IOP, which cannot be shown from the diff.
- verifier: BEHAVIOUR CHANGED for non-POPS users (launcher/src/init.c:245-295 and 338-359; reached from launchPath -> handleBDM -> initModules at launcher/src/handler_bdm.c:31, and from handleQuickboot via initModulesAny at handler_quickboot.c:93 and initModules at handler_quickboot.c:247).

OLD (origin/EMBER init.c:208-287): every loadModules call that was not a cache hit reset the IOP (SifIopReset/SifIopSync), applied sbv_patch_enable_lmb, sbv_patch_disable_prefix_check and sbv_patch_fileio, then loaded exactly the requested module set with the caller's tolerance (0 for initModules, 1 only for initModulesAny). There were no sleeps for USB, MX4SIO or i.Link.

NEW (HEAD): for any request containing Device_USB, Device_MX4SIO or Device_iLink, loadModules first tries a live-IOP path with no reset. forceIOPReset is zeroed at init.c:251, so the guard at init.c:263 is always true and this also applies after initModulesAny.
- It sleeps 3 s if USB is requested (init.c:268-269).
- loadModuleListResident applies only sbv_patch_enable_lmb, runs a "resident" loop that does nothing (init.c:343-350), then loads the entire module list onto the un-reset IOP with tolerant forced to 1 and fileXioInit deferred (init.c:351).
- It sleeps another 3 s (init.c:357), then calls fileXioInit.
- If that returns 0, the IOP is never reset (init.c:271-273).
- Non-Basic driver failures (usbd_mini, usbmass_bd_mini, mx4sio_bd_mini, iLinkman, IEEE1394_bd_mini, bdm, bdmfs_fatfs, ata_bd) are zeroed and do not trigger the fallback.
- Only a Basic-module or fileXioInit failure falls back to the reset path, after msg() has put "ERROR: Failed to initialize module ..." on screen (init.c:459-461).

Provable cost:
- USB: at least +3 s on every launch that is not a cache hit, and +6 s when the live load succeeds.
- MX4SIO and i.Link: +3 s when the live load succeeds.
- Quickboot with a massN: CNF path runs the live path twice (initModulesAny, then initModules), so up to 12 s of sleeps plus a second full module load on the same IOP.

Also changed: the fallback reset path for Device_USB is not identical to EMBER. ata_bd is now tagged Device_USB (init.c:207) while ps2dev9 is not, and on that path tolerant=0, so an ata_bd load failure is fatal. That it fails without dev9 is inference, not verified.

Not shown by the diff: the functional outcome on a standalone console, which depends on what the previous program left resident and on how duplicate module loads behave. The commit (d42763f) cites only the ps2link test console, and the code has no standalone/ps2link distinction despite the commit message implying one.

### [REAL / high] ata_bd is now in the USB module set, so the IOP-reset path for a plain USB launch hard-fails (ata_bd imports dev9, ps2dev9 is not loaded for Device_USB)
- where: launcher/src/init.c:201-208 (INT_MODULE(ata_bd, NULL, Device_ATA | Device_APA | Device_USB)), 175 (ps2dev9 not tagged Device_USB), 294 (reset path keeps caller's tolerant=0), 447-462
- old: ata_bd was loaded only for Device_ATA|Device_APA. A USB launch after IOP reset loaded Basic + bdm + bdmfs_fatfs + usbd_mini + usbmass_bd_mini, all of which resolve on a fresh IOP.
- new: On the reset path loadModuleList(Device_USB, tolerant=0, ...) now also loads ata_bd. ps2dev9 is only tagged ATA|UDPBD|APA|UDPFS|XFROM|SMB, so on a freshly reset IOP the dev9 library is absent; the locally built ata_bd.irx import table (decoded from build/launcher/ata_bd.irx.c) lists 'dev9', so the module cannot link, SifExecModuleBuffer returns <0, and with tolerant=0 init.c:459-461 prints 'ERROR: Failed to initialize module ata_bd' and returns the error. The in-code comment 'Hardware without an HDD skips it via tolerance' (init.c:205) is only true on the live fast path (forced tolerant) or under initModulesAny. Net effect: EMBER's only USB init path (reset then load) no longer works for Device_USB; USB now depends entirely on the live-IOP fast path succeeding. The fast path fails whenever a Basic module (iomanX/fileXio/sio2man/mcman/mcserv) returns <0 or _start==1 on the live IOP - e.g. (expected, not provable from the diff) when launcHER's own Basic modules are already resident because a launcHER.CNF was just read from mc0:/another device, or the caller left iomanX loaded.
- affects non-POPS users: Yes - non-POPS USB launches whenever the fast path does not succeed (likely for quickboot chains where launcHER already initialised modules once, e.g. CNF on memory card with path=mass?:/EMBER/ember.elf). Trigger frequency is inference; the non-tolerant ata_bd load on the reset path is shown by the code.
- verifier: Confirmed, and the trigger is stronger than claimed.

HEAD launcher/src/init.c:207 tags ata_bd with Device_USB (EMBER line 172: Device_ATA | Device_APA only). ps2dev9 (line 175) is not tagged Device_USB. The embedded ata_bd.irx imports dev9.

On the IOP-reset path (line 294, `loadModuleList(device, tolerant, 0, 0)`, tolerant=0 from `initModules`), a Device_USB init therefore stops at ata_bd with "ERROR: Failed to initialize module ata_bd" (lines 447-461) before usbd_mini and usbmass_bd_mini load. Tolerance applies only on the new live-IOP fast path (line 351) and under `initModulesAny`. EMBER's reset-then-load sequence for USB no longer succeeds through `initModules(Device_USB)`.

The fast path fails whenever launcHER's own iomanX is already resident: `loadModuleListResident` does not skip resident modules, the embedded iomanX `_start` returns 1 when its library is already registered, and line 441 treats that as fatal for a Basic module.

This happens with no POPS involvement in at least two EMBER flows:
- launcHER.CNF on a memory card with a mass:/usb: target: handler_quickboot.c:247 `initModules(Device_MemoryCard)`, then :420 `launchPath` -> handler_bdm.c:31 `initModules(Device_USB)`.
- OPL/RiptOPL massN: start: handler_quickboot.c:93 `initModulesAny`, then :247 `initModules(Device_USB)`.

In both, the USB launch fails on HEAD where EMBER reset the IOP and loaded Basic + bdm + bdmfs_fatfs + usbd_mini + usbmass_bd_mini.

Not shown from the repository: that loadcore rejects a duplicate same-version library registration, and that a failed import link returns a negative value from SifExecModuleBuffer. Both are standard IOP behaviour. Nothing was run on hardware. A first, direct USB launch depends on the IOP state left by the chain-loader, which is inference.

Fix direction: drop Device_USB from ata_bd on the reset path, or make ata_bd tolerant/optional there and load ps2dev9 with it; and make the fast path actually skip resident Basic modules.

### [REAL / medium] Any command-line target that is not '<device>:...{.elf,.irx}' now goes through the POPS candidate resolver (memory-card probing before IOP init, a .VCD attempt first, real error code replaced by -ENOENT)
- where: launcher/src/main.c:72-75, 88-100; common/src/launch_args.c:264-360 (pops_detect_bdma_mode), 545-878, 880-883
- old: main called launchPath once on the target and reported its actual return code. No file I/O happened in main before a handler ran initModules. Unknown/bare targets failed immediately with -ENODEV.
- new: (1) pops_resolve_candidate_targets unconditionally calls pops_detect_bdma_mode first, which does up to 36 fopen() probes on mc0:/mc1: POPSTARTER and POPS directories (5 marker + 4 driver names x 4 dirs) on the live, not-yet-initialised IOP. (2) Device targets with no/other extension (e.g. 'mc0:/BOOT/BOOT', 'hdd0:part:PATINFO', any ELF not named *.elf) are tried as '<target>.VCD' first - a full handler pass including module init and file probe - then as given. (3) Bare/unknown-prefix targets (Device_None) are turned into up to 16 POPS guesses (hdd0:__.POPS:pfs:/<name>.VCD, .../IMAGE.VCD, pfs0:, hdd0:PP.<name>, mass0:/POPS/..., mc?:/POPS/...) that are each launched via launchPath (IOP resets, HDD init); the original string itself is not among the candidates. (4) If every candidate fails, main reports -ENOENT (main.c:99) instead of the handler's real error. (5) A launcher or target whose file name starts with XX. or SB. sets global POPS flags (main.c:72-75); I found no non-POPS reader of those flags. Device paths ending in .elf/.irx still take the old single launchPath call (main.c:83-86), so the documented Ember command lines are preserved.
- affects non-POPS users: Partly - only for targets not ending in .elf/.irx: extra delay and a wasted first attempt, different on-screen error code, and failed/typo targets may now boot a PS1 image if one exists at a guessed location. Standard '<device>:/path/app.elf' launches are unaffected by this hunk.
- verifier: Behaviour changed for explicit command-line targets only (launcher invoked with argv[1]); CNF quickboot (no arguments), .cnf/.cfg targets, and `<known device>:...` targets ending in .elf/.irx are unaffected by this hunk.

Old (EMBER main.c): one `launchPath(argc, argv)` call on the target, its real return code reported; no file I/O in main; unknown or bare targets failed at once with -ENODEV.

New (HEAD launcher/src/main.c:83-102, common/src/launch_args.c:264-356, 545-883): any target that is not `<known device>` + .vcd/.elf/.irx goes through `pops_resolve_candidate_targets`.

1. `pops_detect_bdma_mode` first does up to 36 fopen() probes on mc0:/mc1: POPSTARTER and POPS directories, before any handler initialises modules. Time cost is unmeasured.
2. Device targets with another or no extension (.KELF, .XLF, extensionless) are tried as `<target>.VCD` first, then as given.
   - mc targets: the extra cost is one failed open; the second pass reuses the cached module set (init.c:248-250), so there is no second IOP reset.
   - BDM and PFS targets: the device wait or mount is repeated.
   - `hdd?:<part>:PATINFO` targets: still boot on the first candidate, because parsePATINFO truncates at the second colon (common/src/patinfo.c:95-98). Only the MC probes are added.
3. `rom?:` targets (documented as supported, launcher/README.md:16) are broken when passed directly. `rom0:X` is first launched as `rom0:X.VCD` via execROMPath -> `LoadExecPS2` (init.c:535-559), which does not return, so the real ROM path is never tried. The on-console result is firmware-dependent (speculation).
4. Bare or unknown-prefix targets, which already failed on EMBER with -ENODEV, are now expanded into up to 16 POPS .VCD guesses (hdd0:__.POPS, pfs0:, hdd0:PP.<name>, mass0:/POPS, mc?:/POPS, ...). Each is run through launchPath, including HDD/IOP init, and the original string is not among them. A PS1 image at a guessed location would boot.
5. If every candidate fails, main reports -ENOENT (main.c:99) instead of the handler's real error.
6. A launcher or target file name starting with XX. or SB. sets global POPS flags (main.c:72-75). The only reader outside handler_pops.c is init.c:384, gated on `sonySio2`, which is 0 on the non-POPS module path, so this has no non-POPS effect.

Not a regression: a bare `cdrom` target, because CDROM and OSDM are forced OFF in the top-level CMakeLists.txt on both EMBER and HEAD.

Net for a user who never launches POPS: `.elf`/`.irx` command lines and CNF quickboot are preserved; KELF/XLF/extensionless targets still launch after MC probes and one wasted attempt; direct `rom?:` targets no longer execute the requested binary; failure cases are slower and show -ENOENT.

### [REAL / low] UDPBD/UDPFS console IP lookup now prefers mc?:/POPSTARTER and mc?:/POPS over mc?:/SYS-CONF and parses the file differently
- where: launcher/src/init.c:585-612 (initSMAPArguments); launcher/include/ipconfig_smap.h:8-35
- old: Opened mc0:/SYS-CONF/IPCONFIG.DAT, else mc1:; read 15 bytes with newlib open/read; failed if fewer than 15 bytes were read; took everything up to the first whitespace as the IP without validation; did not look anywhere else.
